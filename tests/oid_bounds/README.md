# OID request and reply byte extents

Run `powershell -NoProfile -ExecutionPolicy Bypass -File tests/oid_bounds/Run-Bounds.ps1 -Arch x64` and repeat with `-Arch x86`. Optional `-SourceRoot` selects a checkout and `-OutputDirectory` selects a fresh evidence directory. Default outputs have unique names under `tests/bin/oid_bounds`. Existing evidence directories are refused.

The fixture compiles the complete actual SDK translation unit, constructor, WOW64 handle mapping, request method and C export. It exercises GET and SET through both C and C++ entry points with unrestricted generic OIDs. The 32-bit process must run on 64-bit Windows and report its genuine WOW64 branch; x64 reports native.

Each architecture requires 978 checks. Existing input controls cover zero lengths and values beyond the signed IOCTL byte extent, rejecting before event creation, allocation, payload copying or IOCTL submission. Caller bytes and canaries remain unchanged. The exact INT_MAX serialized extent reaches a controlled allocator or IOCTL refusal without allocating gigabytes or accessing the claimed payload. Valid one-, four- and eight-byte requests retain generic OID behavior and short replies.

The reply matrix covers immediate and pending GET/SET success with returned Length equal to capacity+1 or MAXDWORD at capacities one and eight. Both branches must reject these results with ERROR_INVALID_DATA. WOW64 must preserve all caller bytes, including Length, and never copy malformed results back. Native calls use the caller buffer directly: the fixture requires rejection but does not claim transactional native output. Successful zero-, short- and exact-length replies remain valid; WOW64 SET retains its existing unchanged caller Length and payload behavior. Immediate/pending terminal failures carrying malformed metadata preserve their original error. Deliberate free/CloseHandle error clobbering verifies cleanup cannot replace the selected validation or terminal error.

Win32 device I/O, completion and event/handle recording are substituted. SDK staging allocations are bounded to one MiB and end at a guard page. After fixed-size constructor/enumeration setup, every SDK OID memmove must fit both a registered caller extent and/or tracked allocation extents. Unknown or oversized source/destination ranges are recorded and blocked before access, including a one-byte overrun. Dedicated shim controls verify capacity+1/MAXDWORD copies are blocked and exact copies work. The fake driver publishes requested metadata but writes at most captured payload capacity, and pending writes occur at terminal completion. Any unexpected blocked copy or caught access fault fails a regression assertion.

No driver is loaded, no large request is sent, and no historical unsafe OID code or ablation is executed. Source proof of the pre-fix unchecked copy precedes bounded fixed-code GREEN checks. These are source-level SDK checks, not live NDIS or kernel validation.

The maintained runner records numeric build/child exits, actual branch, a complete assertion/footer count, unchanged source/fixture hashes and a 30-second execution limit. Compilation errors, timeouts, abnormal exits and inconsistent output never count as a passing test.
